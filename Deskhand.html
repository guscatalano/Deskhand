Deskhand is an MCP server that exposes UI Automation, screen capture, and synthetic input for a single Windows machine — covering both the normal desktop and the secure desktop (UAC, lock, and logon). Built on .NET 8 and FlaUI, with a backend seam left open so a fleet — and later an RDP — server can reuse the same tool surface. No code written yet; this is the design.

01

Scope & priorities

The first deliverable is one machine, done thoroughly. A single MCP endpoint exposes three capability families for the local Windows box the model is driving:

  • UIA introspection & control — walk the accessibility tree, query elements, and invoke control patterns (Invoke, Value, Toggle, ExpandCollapse, Selection, Scroll, Window…) via FlaUI.
  • Screen capture — full monitor, single window, or a single element's rectangle, returned as image content with coordinate + DPI metadata.
  • Synthetic input — mouse move / click / drag / scroll and keyboard typing / chords, injected into the target desktop's real input stream.

Two requirements shape this version specifically, and both are treated as first-class rather than deferred:

  1. Cover the local (Default) desktop and the secure desktop. Most tools stop at the normal desktop and go blind the moment a UAC prompt, the lock screen, or the logon UI appears. Deskhand follows input onto the secure desktop and keeps seeing — within the honest limits the OS enforces (§05).
  2. Keep remote open. Nothing in the single-machine build may hard-code "local only." The command layer sits behind a backend seam so a networked fleet agent and, later, a protocol-level RDP server can implement the identical tool contract (§08).

Non-goals for v1

  • No fleet routing, no remote transport yet — designed for, not built.
  • No stealth or anti-detection behavior. Deskhand announces its presence; it isn't built to imitate a human to software trying to tell the difference.
  • No defeating OS security gates. Secure-desktop coverage uses the supported SYSTEM + signed-accessibility paths (§05); where Windows denies synthetic input to the consent UI, we surface that, we don't bypass it.
02

Why .NET and FlaUI

Windows UI Automation is a COM API that lives closest to C++/.NET. FlaUI is a mature .NET wrapper over UIA2/UIA3 giving typed AutomationElements and control-pattern objects instead of raw COM interop — the right spine, and the reason not to reinvent the wrapper. Staying on .NET also puts the rest within reach: SendInput, Windows.Graphics.Capture, GDI, and the desktop/window-station APIs (OpenInputDesktop, SetThreadDesktop) are all plain P/Invoke; the ModelContextProtocol C# SDK provides the server plumbing and both transports; and the agent ships as one signed, self-contained executable. Python would fight the platform on every one of these.

03

The desktop model — the thing that shapes everything

The load-bearing facts sit below the "session" most tools stop at. An interactive Windows session contains one window station, Winsta0, which holds several desktop objects. Two matter:

  • Winsta0\Default — the normal desktop, where the user's apps live. This is what everyone automates.
  • Winsta0\Winlogon — the secure desktop. UAC consent prompts, the lock screen, the logon UI, and Ctrl+Alt+Del all render here.

Only one desktop is the input desktop at any instant, and input flips to Winlogon whenever the system escalates, locks, or logs on. Two rules follow, and together they force the whole process layout:

  • A user-session process on Default cannot see or touch Winlogon. Reaching the secure desktop needs a SYSTEM process in the console session that can open that desktop and set its thread to it.
  • Neither of those can run from an isolated Session 0 service — since Vista, services there have no interactive desktop at all. The service can only supervise and spawn; the real work happens in processes it launches into the session.
04

Covering the local (Default) desktop

This is the main path and where most calls land. The Session Agent runs under the logged-in user's token on Winsta0\Default and holds all three engines: FlaUI over UIA3 for the tree and control patterns, Windows.Graphics.Capture for images, and SendInput for mouse and keyboard. It declares Per-Monitor-v2 DPI awareness in its manifest so the pixels it reasons about match what capture returns and where input lands — no silent scaling drift across mixed-DPI monitors.

Elevated windows on the Default desktop

A medium-integrity Session Agent can't send input to — or fully read — a high-integrity elevated window; that's User Interface Privilege Isolation. To automate elevated apps the agent must itself run elevated, or ship as a signed binary with uiAccess="true" under Program Files. This is distinct from the secure desktop below; an elevated app's window can sit on the Default desktop even though its UAC prompt appeared on the secure one.

05

Covering the secure desktop — honestly

This is the capability most tools skip. It's buildable, but it comes with real gates, and the design's job is to be exact about which parts are reliable and which the OS deliberately restricts.

The mechanism

The Secure Helper runs as SYSTEM inside the console session (the broker duplicates a suitable SYSTEM token for that session rather than acting from its own Session-0 window station). From there it can OpenInputDesktop / OpenDesktop("Winlogon") and SetThreadDesktop onto the secure desktop, then operate on it:

  • Capture — reliable. A SYSTEM thread bound to the secure desktop can BitBlt the desktop DC to read its pixels (the UAC prompt, the lock screen, LogonUI). This is why the secure path uses GDI capture rather than WGC/DXGI, which are restricted on that desktop. So "take a screenshot during a UAC prompt" returns the actual prompt.
  • Reading the tree — partial. Some UIA is available for LogonUI/consent elements from a SYSTEM context, but coverage varies by build; capture + coordinates is the dependable fallback for the secure desktop.
  • Input — gated. Windows specifically hardens the consent UI against synthetic input. The supported way to drive it is a signed uiAccess accessibility application installed in a trusted location, and even then admin policy (e.g. the secure-desktop / consent-prompt Group Policy settings) governs whether it's permitted. Deskhand implements that supported path; where policy denies input to the consent button, it reports secure_input_denied and does not attempt to bypass the gate.
Logon automation — use the right door

Typing credentials into the logon screen via synthetic keystrokes is fragile and mostly blocked. For test rigs and kiosks that must log in unattended, the robust, supported mechanism is a custom Credential Provider (or configured autologon) — a first-class Windows extension point — not fake keypresses at LogonUI. Deskhand exposes secure-desktop capture and state everywhere; genuine logon automation is steered toward the credential-provider path.

Why this isn't a security bypass

Every secure-desktop capability requires SYSTEM (the machine's owner already has that) and a signed accessibility binary and admin-set policy. It grants an administrator automation of a machine they already fully control; it does not let an unprivileged user escalate, and it doesn't defeat any consent gate the administrator hasn't explicitly opened. That's the line, and the design stays on the correct side of it (§13).

06

Following the input desktop

With two desktops covered, the server has to route each command to the process that actually owns the surface in view. The broker tracks the input desktop and exposes its state, so a capture taken mid-UAC returns the prompt and input is refused when nothing can legally receive it.

07

Single-machine architecture & addressing

On one box the wiring is deliberately small. The MCP host launches the MCP server as a stdio child; the server bridges over a local, ACL'd named pipe to the Broker Service, which routes to the Session Agent or Secure Helper per §06. No network, no certificates, no listening sockets — but the same command objects that a remote transport will carry later.

The element-handle problem

UIA AutomationElements are live COM references that don't survive the trip to a model, and their RuntimeId is only stable while the element exists. So a tool never returns a raw pointer: it returns an opaque elementRef that maps, agent-side, to a cached element and a re-resolution recipe — a selector chain of ControlType / AutomationId / Name plus sibling index from a stable root. A stale token re-resolves silently; if that fails, the tool returns a typed stale_element error telling the model to re-query rather than acting on the wrong node. Subtree property reads are batched with a UIA CacheRequest to collapse many cross-process hops into one.

Design principle

Prefer element-anchored actions over raw coordinate clicks on the Default desktop: invoking a button through its UIA pattern is resolution-independent and survives window moves. Coordinate input is the vision path — for the secure desktop, poor UIA trees, and the future RDP backend — and every capture returns bounding rectangles and DPI so a pixel the model sees maps to a point it can click.

10

Screen-capture pipeline

Three capture APIs exist and none wins everywhere, so the agent carries all three and picks per request and per desktop:

Every image returns with its source rectangle, monitor id, DPI scale, and the desktop it came from. Full-screen shots default to quality-tuned JPEG/WebP with optional downscaling to respect the model's context budget; element and window shots stay PNG for text fidelity. A redaction hook can mask configured regions before an image ever leaves the process.

11

Input engine

Synthetic input goes through SendInput — real WM_INPUT events indistinguishable from hardware. Two details make it correct rather than approximate: absolute mouse events normalize to 0–65535 across the whole virtual desktop with MOUSEEVENTF_VIRTUALDESK so secondary monitors are addressable, and the agent's Per-Monitor-v2 DPI awareness keeps its coordinates in the same physical pixels capture reported. On the secure desktop, input runs through the gated uiAccess path of §05 or is refused with secure_input_denied; when the workstation is merely locked, input is off and capture stays on.

Deliberate omission

No "human-like" jitter, curved paths, or randomized timing. Those exist to defeat automation detection, and building them shades the tool toward deception. Deskhand's motion is functional and honest.

13

Security, consent & audit

Even on one machine, this is full local control plus screen capture — and the secure-desktop coverage raises the stakes further. Be honest that it's legitimate (RPA, QA, assistive tech, kiosk, supervised IT) and shaped exactly like something that isn't. The controls are part of the design:

  • Local trust boundary. The stdio→named-pipe channel to the broker is ACL'd to the launching user; the broker validates its callers rather than trusting any local process.
  • Capability flags. Input and capture can be disabled independently; the secure-desktop capability is off by default and enabled only by explicit admin policy plus the signed uiAccess binary.
  • Consent & visibility. A tray presence shows when Deskhand is connected and flashes on active control; capture is treated as sensitive and can require a per-session opt-in.
  • Audit. Every tool call — action, arguments, target desktop, and a hash of any returned image — is written to an append-only log.
  • Kill switch. A local hotkey instantly revokes control and drops the broker channel.
  • Signed binaries. Required throughout, and mandatory for the uiAccess secure-desktop path.
Operating boundary

For authorized use on a machine whose owner has consented. Secure-desktop coverage is admin-gated and non-bypassing by construction; there's no anti-detection behavior; presence is visible. Those aren't limitations to engineer around later — they're what keeps the tool distinct from the thing it resembles.

Delivery roadmap

Phase 1 · Prove the spine

Default desktop, end to end

MCP server (stdio) → broker → Session Agent. UIA read, WGC capture, and SendInput working on the local Default desktop. The IAutomationBackend seam exists from day one.

Phase 2 · The hard part

Secure desktop coverage

SYSTEM Secure Helper, GDI capture of Winlogon, input-desktop auto-follow and desktop state, and the gated uiAccess input path with its policy checks.

Phase 3 · Make it reliable

Handles, patterns, DPI, safety

The elementRef resolver, full control-pattern coverage, Per-Monitor-v2 correctness, capture-budget encoding, and the security controls of §13 — audit, consent, kill switch.

Phase 4 · Kept open

Fleet agent

The same in-session code behind a gRPC/mTLS FleetAgentBackend with outbound-dialing agents and a central registry. No tool-contract change.

Phase 5 · Kept open

RDP protocol backend

An RdpProtocolBackend that dials RDP to a host and drives it over the wire with no software on the target — advertising the capture + input subset of the same contract.
